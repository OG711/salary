# Product Requirements Document (PRD)
## Проект: FinanceTracker (Трекер доходов и расходов)

---

## 1. Обзор проекта (Overview)

### 1.1 Назначение продукта
Веб-приложение для удобного ручного учёта личных финансов, разделения потоков на доходы и расходы по категориям, а также анализа финансового состояния за различные периоды.

### 1.2 Целевая аудитория
Индивидуальный пользователь (на этапе MVP — для личного использования без сложной многопользовательской логики, с возможностью масштабирования до Auth в v1.1).

### 1.3 Основные проблемы, которые решает продукт
* Отсутствие единого наглядного места для фиксации разрозненных трат и доходов.
* Непонимание структуры расходов (сколько уходит на аренду, коммуналку, продукты).
* Необходимость гибкой ручной фиксации нестандартных доходов (подработки, вклады).

## 2. Архитектура и стек технологий (Tech Stack)

* **Frontend:**
  * **Фреймворк:** React (SPA) + Vite.
  * **Стилизация:** Tailwind CSS (быстрая адаптивная вёрстка) + Lucide React (иконки).
  * **Работа с состоянием и API:** TanStack Query (React Query) + Axios (или Fetch).
  * **Визуализация данных:** Recharts или Chart.js (для круговых и столбчатых диаграмм).
* **Backend:**
  * **Среда выполнения:** Node.js (TypeScript или JavaScript ES Modules).
  * **Фреймворк:** Express.js или Hono (Hono идеально подходит для Serverless на Vercel).
  * **ORM / Клиент БД:** Drizzle ORM (наиболее производительный и нативный выбор для Turso/libSQL) или `@libsql/client`.
* **База данных:**
  * **Turso (libSQL / SQLite на Edge):** Быстрая облачная база с бесплатным щедрым тарифом.
* **Инфраструктура и деплой:**
  * **Репозиторий:** GitHub.
  * **Хостинг:** Vercel. 
  * *Архитектурное решение для Vercel:* Монорепозиторий или проект с папкой `/api` (Vercel Serverless Functions) для бэкенда и папкой `/src` для React-клиента, либо раздельные проекты на Vercel.

## 3. Пользовательские сценарии (User Stories)

1. **Добавление расхода:** «Как пользователь, я хочу быстро добавить трату (сумма, категория, дата, комментарий), чтобы зафиксировать покупку продуктов или оплату ЖКХ».
2. **Добавление дохода:** «Как пользователь, я хочу зафиксировать поступление (зарплата, проценты по вкладу, фриланс), чтобы знать текущий баланс».
3. **Просмотр баланса:** «Как пользователь, я хочу видеть на главном экране текущий баланс, сумму доходов и расходов за выбранный месяц».
4. **Аналитика трат:** «Как пользователь, я хочу видеть круговую диаграмму расходов по категориям, чтобы понимать, куда уходит больше всего денег».
5. **История операций:** «Как пользователь, я хочу просматривать список операций с фильтрацией по датам и типам, а также редактировать или удалять ошибочно введённые записи».

## 4. Функциональные требования (Functional Requirements)

### 4.1 Модуль операций (Transactions)
* **Типы операций:** Расход (`expense`), Доход (`income`).
* **Поля записи:**
  * Сумма (число, с поддержкой сотых долей).
  * Категория (выбор из списка).
  * Дата (по умолчанию текущая, с возможностью выбора прошедшей).
  * Комментарий / Заметка (необязательное текстовое поле).
* **Действия:** Создание, чтение, редактирование, удаление (CRUD).

### 4.2 Модуль категорий (Categories)
* Предустановленные категории:
  * **Расходы:** Продукты, Аренда, Коммуналка (ЖКХ), Транспорт, Развлечения, Здоровье, Другое.
  * **Доходы:** Зарплата, Подработка / Фриланс, Проценты по вкладам / Инвестиции, Подарки, Другое.
* Возможность добавления собственных категорий и выбора цвета/иконки.

### 4.3 Модуль аналитики и дашборда (Dashboard & Analytics)
* Карточки показателей за выбранный период:
  * Общий доход.
  * Общий расход.
  * Чистая разница (Доход − Расход).
* Круговая диаграмма (Pie Chart) долей расходов по категориям.
* Динамика по месяцам (Bar Chart: Доходы vs Расходы).
* Фильтр по периодам: текущий месяц, прошлый месяц, год, произвольный диапазон.

## 5. Модель данных (Database Schema)

### Таблица `categories`
| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | `INTEGER PRIMARY KEY AUTOINCREMENT` | Идентификатор |
| `name` | `TEXT NOT NULL` | Название категории |
| `type` | `TEXT NOT NULL` | `'income'` или `'expense'` |
| `color` | `TEXT` | HEX-код цвета (для диаграмм) |
| `icon` | `TEXT` | Название иконки (Lucide) |

### Таблица `transactions`
| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `id` | `INTEGER PRIMARY KEY AUTOINCREMENT` | Идентификатор |
| `amount` | `REAL NOT NULL` | Сумма транзакции |
| `type` | `TEXT NOT NULL` | `'income'` или `'expense'` |
| `category_id`| `INTEGER REFERENCES categories(id)` | Связь с категорией |
| `date` | `TEXT NOT NULL` | Дата операции (ISO 8601: `YYYY-MM-DD`) |
| `note` | `TEXT` | Описание / комментарий |
| `created_at`| `TEXT DEFAULT CURRENT_TIMESTAMP` | Время добавления в систему |

## 6. Спецификация Backend API (REST)

Все операции с базой производятся исключительно через Node.js API:

### Категории:
* `GET /api/categories` — получить список категорий (с фильтрацией по query-параметру `?type=income|expense`).
* `POST /api/categories` — создать новую категорию.
* `DELETE /api/categories/:id` — удалить категорию.

### Транзакции:
* `GET /api/transactions` — получить список операций. Поддерживает параметры пагинации и фильтрации: `?startDate=...&endDate=...&type=...&categoryId=...`.
* `POST /api/transactions` — создать операцию (валидация входных данных на бэкенде).
* `PUT /api/transactions/:id` — обновить операцию.
* `DELETE /api/transactions/:id` — удалить операцию.

### Аналитика:
* `GET /api/analytics/summary?period=2026-10` — агрегированные данные (суммарный доход, расход, разбивка по категориям для графиков). Расчёт производится на стороне сервера SQL-запросами с `GROUP BY`.

## 7. Нефункциональные требования (NFR)

1. **Производительность:** Время отклика API < 150 мс благодаря использованию libSQL Edge DB (Turso).
2. **Адаптивность (Mobile-First):** Удобный ввод со смартфона (так как траты часто вносятся «на ходу»).
3. **Безопасность конфигурации:** Все секреты (URL БД, токены Turso `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`) хранятся в `.env` локально и в **Environment Variables** на Vercel.
